Golden rules. 1) Never work directly on main. 2) Commit small and often. 3) Pull before you push. 4) Never rewrite history that others have pulled. 5) Never commit secrets (passwords, keys, .env).

How Git thinks

Your files move through four places. Most commands just move changes from one place to the next.

  1. Working folderfiles you edit
  2. Staging areagit add
  3. Local repogit commit
  4. Remotegit push (Bitbucket)

main is the stable branch, HEAD is where you are now, and origin is the nickname of the remote repo.

Setup and SSH

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git --version

SSH lets you push without typing a password each time:

ssh-keygen -t ed25519 -C "you@example.com"
cat ~/.ssh/id_ed25519.pub     # copy this output

In Bitbucket, open your personal settings, find SSH keys, add the key, then test:

ssh -T git@bitbucket.org
Prefer SSH. HTTPS also works, but it needs a token or app password, and Bitbucket's sign-in options change, so check their docs if it asks for credentials.

Create and clone repos

Clone an existing repo (most common on a new job)

git clone git@bitbucket.org:team/project.git
cd project
git branch -a          # see all branches

Create a new repo in Bitbucket

Use the Create button, choose Repository, give it a name, choose private or public, and create it. Menu names can differ slightly.

Start a repo from existing local code

cd my-project
git init
git add .
git commit -m "Initial commit"
git remote add origin git@bitbucket.org:team/my-project.git
git push -u origin main
Add a .gitignore before your first commit (see Extras) so node_modules and .env never get in.

Daily workflow

git pull                      # get the latest first
git status                    # what changed?
git diff                      # see the exact changes
git add file.js               # stage one file  (git add . stages all)
git commit -m "Add retry to file upload"
git push
git log --oneline --graph     # history at a glance
Good commit messages: short, present tense, say what and why. Fix null error in token refresh beats changes.

Branches

Create and switch

git switch -c feature/login-fix        # create and move to it
git switch main                        # move back
git branch                             # list local branches
git push -u origin feature/login-fix   # publish it the first time

Delete a branch

git branch -d feature/login-fix              # local, only if merged
git branch -D feature/login-fix              # local, force (unmerged work is lost)
git push origin --delete feature/login-fix   # remote

Naming: feature/, bugfix/, hotfix/, followed by a short description or ticket ID, such as feature/PROJ-123-export-csv.

You cannot delete the branch you are standing on. Switch to main first.

Merging

Bring your finished branch into main:

git switch main
git pull
git merge feature/login-fix
git push
  • Fast-forward: main had no new commits, so Git just moves the pointer.
  • Merge commit: both sides have changes, so Git adds a commit joining them (--no-ff forces this).
  • Squash: git merge --squash branch turns all commits into one, which keeps history tidy.
git merge --abort     # changed your mind mid-merge

Merge conflicts

A conflict happens when you and a teammate change the same lines. Git stops and asks you to choose. It is normal, not an error.

git pull origin main
# CONFLICT (content): Merge conflict in app.js

Open the file. Git marks both versions:

<<<<<<< HEAD
const limit = 50;          // your version
=======
const limit = 100;         // their version
>>>>>>> main
  1. Find the markers (git status lists conflicted files).
  2. Edit the file to the final correct code, and delete all three marker lines.
  3. Run and test the code.
  4. git add app.js
  5. git commit (or git merge --continue), then git push.
Stuck? Run git merge --abort to go back to before the merge. If the conflict is in your teammate's logic, message them and fix it together. VS Code has Accept Current / Incoming / Both buttons.
Avoid big conflicts: pull from main into your branch every day, keep branches short, and keep commits small.

Pull requests in Bitbucket

  1. Push your branch: git push -u origin feature/login-fix
  2. In Bitbucket, choose Create pull request. Check that the source is your branch and the destination is main (or develop).
  3. Write a clear title and a description: what changed, why, and how to test.
  4. Add reviewers and link the Jira ticket if your team uses one.
  5. Create the pull request and wait for review.
  6. Reviewers comment and approve. Fix comments by committing to the same branch: the pull request updates itself.
  7. When approved and checks pass, click Merge. Pick the strategy your team uses (merge commit, squash or fast-forward) and tick Close source branch.
  8. Update your machine: 
    git switch main
git pull
git branch -d feature/login-fix

Conflict shown in the pull request?

git switch feature/login-fix
git pull origin main         # brings main into your branch
# fix conflicts, then:
git add .
git commit
git push                     # the pull request refreshes
Keep pull requests small (under about 400 changed lines). Small ones get reviewed faster and break less.

Rebase and cherry-pick

git switch feature/login-fix
git rebase main             # replay your commits on top of latest main
git push --force-with-lease # needed after a rebase, on YOUR branch only
Never rebase or force-push shared branches like main or develop. It rewrites history other people have pulled.

Cherry-pick copies one commit onto your current branch, which is useful for hotfixes:

git cherry-pick a1b2c3d

If a rebase goes wrong: git rebase --abort.

Undo mistakes

SituationCommand
Discard edits to a filegit restore file.js
Unstage a filegit restore --staged file.js
Fix the last commit message or add a forgotten file (not yet pushed)git commit --amend
Undo last commit, keep the changesgit reset --soft HEAD~1
Undo a commit that is already pushed (safe)git revert a1b2c3d
Throw away all local changes and commitsgit reset --hard origin/main
Pause work without committinggit stash, later git stash pop
Lost a commit after a mistakegit reflog, then git switch -c rescue a1b2c3d
revert adds a new commit that undoes an old one, so it is safe on shared branches. reset --hard deletes work, so use it only when you are sure.

Tags and versioning

A tag is a permanent label on a commit, usually a release.

git tag -a v1.2.0 -m "Release 1.2.0"
git push origin v1.2.0        # or: git push --tags
git tag                       # list tags
git switch --detach v1.2.0    # look at the code as it was

Semantic versioning: MAJOR.MINOR.PATCH

  • PATCH (1.2.1): bug fix, nothing breaks.
  • MINOR (1.3.0): new feature, still compatible.
  • MAJOR (2.0.0): breaking change.

Common team flow: feature/* branches merge into develop, develop merges into main for a release (tagged), and urgent fixes use a hotfix/* branch from main. Follow whatever your team uses.

Deleting repositories

Deleting a repo on Bitbucket removes its code, history and pull requests, and usually cannot be undone. Only do it for your own test repos, and only if you have admin rights.
  • Bitbucket: open the repo, go to Repository settings, find Delete repository, and confirm by typing the name.
  • Local copy: a repo is just a folder, so deleting the folder removes only your copy (rm -rf project on Mac/Linux). The remote stays.
  • Safer first: clone a backup, or archive or rename the repo, if you are unsure.

Extras you will need

fetch vs pull

git fetch downloads changes without touching your files. git pull is fetch plus merge. Fetch first when you want to look before you merge.

.gitignore

node_modules/
.env
*.log
dist/
.DS_Store

Secrets committed by mistake

If a password or key reached the remote, rotate it immediately (change it), then ask your team how to clean the history. Deleting the file in a new commit is not enough.

Find who changed a line, or when a bug started

git blame app.js
git log -p -- app.js
git bisect start    # binary search for the bad commit

Handy settings

git config --global pull.rebase false
git config --global alias.st status
git config --global alias.lg "log --oneline --graph --all"

Bitbucket Pipelines

Many teams run tests automatically on every push using a bitbucket-pipelines.yml file in the repo. A failed pipeline blocks the merge, so read the log and fix it before asking for review.

Practice lab (about 90 minutes)

Use a throwaway repo, never a real one. Pretend to be two developers by cloning it twice.

  1. Create a Bitbucket repo named git-practice and clone it twice: dev-a and dev-b.
  2. In dev-a, create feature/a, edit line 1 of a file, commit and push.
  3. In dev-b, create feature/b, edit the same line, commit and push.
  4. Raise a pull request for each branch. Merge A first.
  5. Update B with git pull origin main, resolve the conflict, push, and merge B.
  6. Tag the result v1.0.0, delete both branches (local and remote).
  7. Break something on purpose, then fix it with revert, stash and reflog.
  8. Explain the full flow out loud without notes.
When you can do the lab without looking anything up, you are ready for a team repo.
Practice on throwaway repos first. Command menus in Bitbucket can change, so check their docs if a screen looks different.
